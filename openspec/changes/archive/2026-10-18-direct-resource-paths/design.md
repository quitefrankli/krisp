# Design

## Context

See [proposal.md](proposal.md) for the motivation. The agreed implementation is already present in the working tree: `resource_paths.hpp/.cpp` owns lookup, `Config::init` configures it, and Meson generates private engine path constants. This change documents that work rather than scheduling a second implementation.

Before the extraction, `Utility` combined resource lookup, runtime layout, logging, and timing. Development builds assembled a common runtime directory, most recently with a resources symlink. Conan editable consumers share the engine's `build/debug` libraries and must share its defaults without copying assets into application repositories.

## Goals / Non-Goals

**Goals:**

- Keep filesystem layout knowledge in one resource-path module and the engine build, with a small interface for applications.
- Permit independent source asset, generated shader, default configuration, and generated lighting locations.
- Preserve app overrides and explicit path configuration for internal and external applications.
- Keep development reads separate from app-owned writable output.

**Non-Goals:**

- Redesign asset registration, decoding, caching, asynchronous loading, or GPU upload.
- Change ResourceLoader optimization settings or asset formats.
- Refactor logging and timing beyond removing resource-path responsibilities from Utility.
- Turn lexical filename validation into a filesystem security sandbox.
- Require standalone packages to retain access to the development checkout.

## Decisions

### 1. Explicit engine locations, with app-owned paths alongside them

`EnginePaths` contains `resources`, `shaders`, `default_config`, and `environment_lighting`. `RuntimePaths` combines these with `app_resources`, `app_config`, and `writable_data`. Applications can start with `ResourcePaths::paths_for_executable(app_name)` and override their own asset root or any engine location before calling `Config::init`.

Development defaults are absolute paths generated by Meson and compiled into the engine library:

| Field | Location |
| --- | --- |
| resources | Engine source `resources/default` |
| shaders | Selected engine build `shaders` |
| default_config | Engine source `configs/default.yaml` |
| environment_lighting | Selected engine build `tools/default_environment.krisp-ibl` |

A common runtime root with a resources symlink was considered. Explicit paths remove that intermediate directory and staging lifecycle while naturally representing generated and authored files in different locations. A generic mount system would add complexity beyond the two resource owners currently needed.

### 2. One focused resource-path module

`ResourcePaths` owns resource/configuration resolution, resource enumeration, relative-name validation, and the existing test fixture override. Typed lookups select the resource category; explicit category prefixes retain their meaning. Existing app assets win over matching engine defaults. Shader lookup also checks app shaders first. Config reads prefer app files; writes target the app configuration directory.

`Config::init` initializes paths once and then configures Utility logging. Utility retains logging, timing, writable-data access, and save-path helpers. Keeping all lookup in Utility would retain its mixed responsibilities; creating separate resolvers per category would duplicate lookup policy. The existing process-wide initialization model is retained rather than introducing unrelated lifetime changes.

### 3. Editable consumers share defaults from the compiled engine

The engine library supplies its own default locations. Bundled applications set only their app resource directory through their existing source-root configuration. An external editable consumer likewise supplies its own app resource path without engine-specific compile definitions or reconstructed engine checkout paths.

Conan's editable source layout exports `krisp_resources`, `krisp_shaders`, `krisp_default_config`, and `krisp_environment_lighting` through pkg-config custom content. These describe the same source/build locations for inspection and explicit overrides. Editable metadata remains tied to `build/debug`, matching the current Conan library layout. Application integration policy stays in the owning application repository.

Passing engine source/build macros independently to every application was rejected because it duplicates layout knowledge and allows consumers to disagree with the linked engine.

### 4. Generate runtime data without staging it

The runtime Meson target groups shader and environment-lighting generation. Applications and tests depend on those outputs. `scripts/stage_runtime.py` is removed; development requires neither runtime asset copies nor runtime directory symlinks. Asset edits are visible on subsequent filesystem reads; this does not promise hot reload or invalidation of already decoded resources.

Installation assembles actual files only when creating a self-contained package. `development_paths=false` disables embedded checkout paths and uses the executable-relative `krisp-runtime` layout unless explicit engine paths are supplied. This deployment behavior is outside the no-duplication guarantee for local editable development.

## Risks / Trade-offs

- [Checkout or build directory moved] → Reconfigure/rebuild the engine and regenerate consumer Conan metadata; explicit overrides remain available.
- [Generated shaders or lighting absent] → Retain build dependencies on their generation targets; editable consumers must use a built engine checkout.
- [Caller interface changes] → Migrate resource/configuration helpers from Utility to ResourcePaths and replace `engine_runtime` with explicit engine fields. Legacy aliases are not retained.
- [Shared source assets accidentally written by tests] → Place writable test fixtures beneath the Debug build directory; treat engine defaults as read-only.
- [Source assets changed after decode] → New filesystem reads see changes; cache invalidation remains an asset-loading concern outside this design.
- [Relative names or symlinks escape intended directories] → Reject empty, absolute, and parent-traversal names. Do not claim canonical-path or symlink confinement.

## Migration Plan

The core extraction, build changes, caller migration, metadata exports, and documentation already exist. The implementation checklist records their current state and the validation performed in the preceding implementation turn. Existing external callers must adopt ResourcePaths for lookup and explicit EnginePaths for custom layouts, regenerate Conan dependency metadata, and rebuild/relink against Krisp.

No asset movement or format migration is required. No changes to external application repositories are part of this change. Rollback, if requested, must be scoped to the resource-path changes and preserve unrelated working-tree edits; there is no automatic rollback or commit in this workflow.
